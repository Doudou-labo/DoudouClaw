# FTS5 vs Elasticsearch : Benchmarks et Analyse Comparative

*État de l'art 2025-2026 pour l'intégration avec SQLite*

---

## Introduction au Problème

### Pourquoi comparer FTS5 et Elasticsearch ?

Le choix entre **SQLite FTS5** (extension embarquée) et **Elasticsearch** (moteur de recherche distribué) s'est imposé comme un dilemme architectural majeur en 2025. Historiquement, les développeurs confrontés à des besoins de recherche full-text robustes se tournaient systématiquement vers la stack Elasticsearch/Solr, perçue comme l'unique option viable pour des performances enterprise.

Cependant, plusieurs facteurs ont remis en question cette approche :

1. **Complexité opérationnelle** : Déployer une JVM, gérer un cluster, configurer les shards et replicas représente une charge significative pour des projets de taille moyenne.

2. **Latence réseau** : Même avec des optimisations, le saut réseau entre l'application et le moteur de recherche externe introduit une latence incompressible (10-50ms typiquement).

3. **Coûts infrastructure** : Un cluster Elasticsearch minimal en production représente un coût récurrent substantiel (VMs, monitoring, maintenance).

4. **Cas d'usage émergents** : Les applications modernes (mobiles, edge computing, P2P) privilégient des architectures légères sans dépendances externes.

En 2025, des benchmarks terrain (Medium, Jasper Smet) ont démontré que FTS5 pouvait atteindre des performances comparables, voire supérieures, pour des volumes de données modérés—soulevant la question : *pourquoi payer la complexité d'Elasticsearch quand SQLite suffit ?*

## Architecture des Deux Solutions

### SQLite FTS5 — L'Approche Embarquée

FTS5 est une **extension native de SQLite** (intégrée depuis la version 3.9.0, 2015) qui implémente un moteur de recherche full-text directement dans le processus applicatif.

**Principes architecturaux :**

| Caractéristique | Détails |
|-----------------|---------|
| **Stockage** | Index inversé dans un fichier `.db` distinct ou intégré |
| **Indexation** | Algorithme BM25 natif (même que Lucene/Elasticsearch) |
| **Concurrence** | Mode WAL (Write-Ahead Logging) — lectures non-bloquantes |
| **Requêtes** | Syntaxe SQL étendue via opérateur `MATCH` |
| **Tokenizers** | Unicode61, Porter, ASCII (configurable) |
| **Fonctions auxiliaires** | `snippet()`, `highlight()`, `bm25()` pour résultats enrichis |

**Structure d'un index FTS5 :**
```sql
CREATE VIRTUAL TABLE docs_fts USING fts5(
  title, 
  body, 
  tags,
  tokenize='unicode61'
);
```

FTS5 maintient un **index inversé** (inverted index) en mémoire-mappée : chaque terme pointe vers les documents le contenant, avec métadonnées de position pour les requêtes de proximité.

### Elasticsearch — L'Approche Distribuée

Elasticsearch repose sur **Apache Lucene** et offre une architecture distribuée conçue pour le Big Data.

**Principes architecturaux :**

| Caractéristique | Détails |
|-----------------|---------|
| **Stockage** | Segments Lucene sur disque, répliqués sur nœuds |
| **Indexation** | BM25 + scoring personnalisable + aggregations |
| **Concurrence** | Architecture maître-esclave avec élection de leader |
| **Requêtes** | DSL JSON via API REST |
| **Scalabilité** | Horizontal (sharding) + vertical (plus de RAM/CPU) |
| **Écosystème** | Kibana (viz), Logstash (ingestion), Beats (agents) |

**Composants clés :**
- **Cluster** : Ensemble de nœuds
- **Index** : Collection de documents (équivalent à une table FTS5)
- **Shard** : Partition d'un index pour distribution
- **Replica** : Copie de sécurité et load-balancing

## Benchmarks de Performance

### Méthodologie

Les benchmarks 2025 s'appuient sur des jeux de données réels :
- **Volume testé** : 7 000 à 1 000 000+ documents
- **Métriques** : Latence P50/P99, requêtes/seconde (RPS), overhead mémoire
- **Charge** : 50 connexions concurrentes, 8 threads

### Résultats Clés

#### 1. Latence (Temps de Réponse)

| Moteur | Latence Médiane | Latence P99 | Contexte |
|--------|-----------------|-------------|----------|
| **FTS5** | 1-5 ms | <10 ms | Local, WAL mode |
| **FTS5 (benchmark Jasper Smet)** | 57 ms | 83 ms | 7K docs, 50 connexions |
| **Elasticsearch** | 10-50 ms | 100-500 ms | Cluster distant |
| **Elasticsearch (cluster chargé)** | 100-300 ms | >1s | Sous charge élevée |

**Observation** : Un article de Medium (nov. 2025) rapporte une amélioration de **100× sur la latence médiane** en migrant d'Elasticsearch vers FTS5 : passage de ~500ms à moins de 5ms.

#### 2. Throughput (Requêtes par Seconde)

| Configuration | RPS | Notes |
|---------------|-----|-------|
| FTS5 (local) | 840+ | 7K documents, 50 connexions |
| Elasticsearch (3 nœuds) | 1000-10000+ | Dépend fortement du dimensionnement |

**Analyse** : Sur des volumes modestes (<1M docs), FTS5 offre un throughput comparable sans infrastructure dédiée.

#### 3. Requêtes Complexes

| Type de Requête | FTS5 | Elasticsearch |
|-----------------|------|---------------|
| **Simple terme** | <1 ms | 5-15 ms |
| **Multi-termes (AND/OR)** | 1-3 ms | 10-20 ms |
| **Fuzzy search** | Limité (tokenizers) | Natif + configurabilité |
| **Prefix matching** | Optimisé via index | Supporté |
| **Filtres combinés** | JOIN SQL classique | Bool queries + aggregations |
| **Recherche sémantique** | Hybride (FTS + vecteurs) | Natif (vector search) |

#### 4. Overhead et Consommation

| Métrique | FTS5 | Elasticsearch |
|----------|------|---------------|
| **RAM requise** | Quelques Mo (cache OS) | 2-8 Go minimum par nœud |
| **CPU** | Utilisation sporadique | Usage constant (JVM GC) |
| **Disque** | Taille index ≈ 30-50% des données | Taille index ≈ 100-150% |
| **Démarrage** | Instantané | 10-60 secondes |

## Limites de Chaque Approche

### Limites de FTS5

1. **Volume maximal** : Pas de sharding natif. Au-delà de **~10 millions de documents**, les performances dégradent linéairement.

2. **Fonctionnalités avancées** :
   - Pas de NLP intégré (analyse sémantique, NER)
   - Pas de suggestion orthographique native (spellcheck)
   - Agrégations limitées par rapport à Elasticsearch

3. **Concurrence écrite** : Mode WAL gère bien les lectures concurrentes, mais les écritures restent séquentielles.

4. **Recherche distribuée** : Impossible de répartir un index sur plusieurs machines.

5. **Monitoring** : Pas d'outils natifs équivalents à Kibana ou Elastic Stack.

### Limites d'Elasticsearch

1. **Complexité opérationnelle** : Nécessite une expertise DevOps (tuning JVM, gestion de cluster, split-brain).

2. **Latence réseau** : Impossible d'éliminer le coût du saut réseau, même en co-localisation.

3. **Coût** : Infrastructure dédiée requise même pour de petits volumes.

4. **Overkill pour les petits projets** : Même un cluster minimal (3 nœuds) est disproportionné pour <100K documents.

5. **Dépendance JVM** : Garbage collection, tuning heap, version Java à maintenir.

## Recommandations par Cas d'Usage

### Choisissez FTS5 si :

| Critère | Seuil indicatif |
|---------|-----------------|
| Volume de données | < 1-5 millions de documents |
| Besoin de latence | < 10 ms critique |
| Ressources ops | Équipe réduite, pas de DevOps dédié |
| Infrastructure | Edge, mobile, P2P, IoT |
| Budget | Contrainte forte (startup, MVP) |
| Pattern d'accès | Lecture-intensive, écritures sporadiques |

**Exemples** : 
- Application mobile avec recherche offline
- CMS de petite/moyenne taille (<500K contenus)
- Outils de documentation interne
- Prototypes et MVPs

### Choisissez Elasticsearch si :

| Critère | Seuil indicatif |
|---------|-----------------|
| Volume de données | > 10 millions de documents |
| Besoin de scalabilité | Croissance imprévisible, pics de charge |
| Fonctionnalités avancées | NLP, analytics, visualisations, ML |
| Haute disponibilité | SLA 99.99%, DR multi-région |
| Équipe | DevOps/SRE dédiés |
| Agrégations complexes | Dashboards temps réel, métriques |

**Exemples** :
- Plateforme e-commerce à grande échelle
- SIEM / Logging centralisé
- Moteur de recherche public web-scale
- Analytics temps réel

### Zone Grise (1-10M documents)

Dans cette fourchette, le choix dépend de facteurs qualitatifs :
- Si l'équipe maîtrise déjà Elasticsearch → poursuivre
- Si simplicité ops est prioritaire → FTS5 avec surveillance
- Si croissance rapide anticipée → Elasticsearch pour l'avenir-proofing
